# Design — CYB-1272 Asset Env Passthrough

## Architecture Context
- **Constraints**: Existing pipeline run APIs already accept `asset_ids`; the change must not alter request/response shapes. Argo manifests are generated by `backend/internal/transpiler` from usecase options. The repository already validates asset existence through `AssetRepository.FindExistingIDs`.
- **Goals**: Give every pipeline node a deterministic asset context contract while keeping the current pipeline run flow intact.
- **Non-Goals**: Add new API endpoints, change Postgres schema, implement retry controls, or solve large-batch admission/queueing.

## Affected Modules
- `backend/internal/usecase/pipeline` - assemble selected asset context and pass it as `transpiler.Options.GlobalEnv`.
- `backend/internal/transpiler` - continue injecting global env into container and script templates.
- `backend/internal/repository` - use existing `AssetRepository.Get` for per-asset details in the first slice.
- `backend/internal/postgres` - no schema changes expected; existing asset reads supply the fields.

## Architecture Decisions

### Decision 1: Extend the existing GlobalEnv path
- **Approach**: Build the complete asset env list in `Usecase.Deploy` after asset validation and pass it through `transpiler.Options.GlobalEnv`.
- **Alternative**: Add a new pipeline runtime API for containers to fetch asset context at startup.
- **Rationale**: The selected assets are already known before Argo submission, and env injection is simple for containers to consume without credentials or network calls.
- **Trade-off**: Env vars are not suitable for very large metadata payloads. This slice keeps metadata bounded to per-asset JSON available on the asset row and defers larger context to a later runtime file or API.
- **Rollback**: Remove the added env fields while preserving existing `ASSET_IDS`, `ASSET_COUNT`, `VIDEO_ID`, and `REQUEST_ID`.

### Decision 2: Keep single-asset reads for the first slice
- **Approach**: Reuse `AssetRepository.Get` in asset order to populate per-asset env details.
- **Alternative**: Add `AssetRepository.BatchGet` and update Postgres plus all mocks in this PR.
- **Rationale**: CYB-1272 is about completing the env contract. Large-batch performance belongs with admission control and batch-run policy work.
- **Risk**: Runs with many selected assets issue one read per asset.
- **Mitigation**: Validate with small-batch dev runs now; document `BatchGet` as a follow-up if batch throughput becomes a bottleneck.

### Decision 3: Add a compact aggregate JSON env
- **Approach**: Add `ASSETS_JSON` containing an ordered array of selected asset summaries while keeping indexed env vars for shell-friendly tasks.
- **Alternative**: Only expose indexed env vars.
- **Rationale**: Indexed env vars are convenient for shell scripts, while structured JSON is easier for Python/Go task code and prevents reassembling fields from many env names.
- **Trade-off**: Large selected batches could make env size too large. For this slice, the payload remains a summary and batch limits are handled separately.

## Data Flow

```text
Run modal / API client submits asset_ids
  -> pipeline handler passes asset_ids to usecase
  -> usecase validates assets via AssetRepository.FindExistingIDs
  -> usecase reads selected assets in order via AssetRepository.Get
  -> usecase builds GlobalEnv:
       ASSET_IDS, ASSET_COUNT, ASSET_0_*, ASSETS_JSON, VIDEO_ID, REQUEST_ID
  -> transpiler injects GlobalEnv into every Argo node template
  -> dry-run manifest and real submitted workflow share the same env contract
```

## Data Model Changes
- None.

## Risks / Trade-offs

| Risk | Impact | Mitigation |
|------|--------|------------|
| Large asset metadata can exceed practical env sizes | Workflow submission may fail or containers may receive unwieldy env | Keep summary fields only; defer large payloads to runtime files/API |
| N+1 asset reads for large batches | Slow run creation for many assets | Keep this first slice small-batch oriented; follow with BatchGet in CYB-1574/CYB-1639 if needed |
| Containers may depend on unstable variable names | Runtime scripts become hard to migrate | Keep names explicit and cover them in manifest tests |
